# Building the AQSMS Android APK

This produces an installable `.apk` for side-loading onto an Android phone
(`adb install`, or the Android Package Installer after copying the file across).

Everything below runs from `frontend/`.

---

## 2. Release signing (do this once)

Release APKs must be signed with the project keystore, **not** Android's public
debug key. The keystore and its passwords live in `frontend/credentials/`, which
is gitignored.

If `frontend/credentials/` is missing, recreate it:

```bash
mkdir -p credentials
"C:/Android/jdk21/bin/keytool.exe" -genkeypair -v \
  -keystore credentials/aqsms-release.keystore \
  -alias aqsms-release \
  -keyalg RSA -keysize 2048 -validity 10950 \
  -dname "CN=Aqua Smart Monitoring System, OU=AQSMS, O=AQSMS, L=Unknown, ST=Unknown, C=PH"
```

`keytool` comes from the JDK 21 in section 1. **Android Studio is not installed
on this machine**, so there is no `C:\Program Files\Android\Android Studio\jbr`
to reach for — and building this APK with a key generated by a different JDK is
the one mistake here that cannot be undone afterwards, because Android
identifies an app by its signing key.

Then write `credentials/keystore.properties`:

```properties
storeFile=aqsms-release.keystore
storePassword=<the password you chose>
keyAlias=aqsms-release
keyPassword=<the same password>
```

> **Back this directory up privately.** Android identifies an app by its signing
> key. If the keystore is lost, a future APK cannot be installed as an upgrade
> over an already-installed copy — users would have to uninstall first, losing
> the saved Pi address and session.

## 3. Build

### One command (this machine)

```powershell
cd C:\Users\Jahna\Music\AQSMS-APP-main
powershell -ExecutionPolicy Bypass -File dev-tools\build-apk.ps1
```

Runs the whole sequence — prebuild → release signing → Gradle → `apksigner
verify` → SHA-256 — against the toolchain paths in section 1. `-Clean` wipes the
generated `android/` first; `-SkipVerify` skips type-check and lint. It refuses
to run if `certs/aqsms-ca.crt` turns out to contain a private key.

### The same steps, by hand

```bash
cd frontend

# a. (Optional but recommended) Enable HTTPS to the Pi.
#    Copies the Pi's public CA certificate into the build so the app trusts
#    exactly that Pi -- see ../PHONE_TO_PI_SETUP.md Part 2.
#    If this file is absent the build still succeeds and warns; the APK will
#    simply not trust the Pi's HTTPS.
mkdir -p certs
scp <pi-user>@<pi-address>:aqsms/pi-server/certs/aqsms-ca.crt certs/aqsms-ca.crt

# b. Generate the native Android project (android/ is build output, not source).
#    The plugin in plugins/with-pi-certificate.js runs here and bundles the
#    certificate from step (a) when it is present.
npx expo prebuild --platform android --no-install

# c. Point the release build at the project keystore.
#    Required after EVERY prebuild — the Expo template defaults to debug signing.
node scripts/apply-release-signing.js
```

```powershell
# d. Build -- paths are this machine's, see section 1.
$env:JAVA_HOME    = "C:\Android\jdk21"
$env:ANDROID_HOME = "C:\Android\Sdk"
$env:PATH         = "$env:JAVA_HOME\bin;$env:PATH"

# -p android runs Gradle without leaving frontend/, so the APK path below never
# depends on the current directory.
.\android\gradlew.bat -p android :app:assembleRelease
```

`android.versionCode` in `app.json` is currently **3** (the role-based release;
2 was the one-account build). Android refuses to install an APK whose
`versionCode` is not higher than the installed one, so bump it before each build
you intend to install over an existing copy. The `versionName` (from
`expo.version`) can stay `1.0.0`.

The APK lands at:

```
frontend/android/app/build/outputs/apk/release/app-release.apk
```

### App icon and splash artwork

`assets/images/icon.png` is the **source** for every launcher and splash image.
It is never written by a script; the rest are derived from it:

```bash
cd frontend
node scripts/make-icons.mjs
```

| Written | From | Used by |
|---|---|---|
| `adaptive-icon.png` | the mark lifted off `icon.png` | `android.adaptiveIcon.foregroundImage` — the icon Android 8+ actually draws |
| `splash-image.png` | the same mark, larger | `expo-splash-screen` |
| `favicon.png` | `icon.png`, full bleed | web |

The script flood-fills inwards from the border to remove `icon.png`'s flat
background, so the droplet (including its dark interior, which the cyan outline
encloses) survives as an alpha channel. The mark is then scaled so that its own
bounding circle fits inside Android's safe zone: a launcher masks the adaptive
layer to a circle on some phones and a squircle on others, and this droplet is
1.25x taller than it is wide, so at 48% of the canvas its tips still clear a
circular mask. Enlarging it there is what clips the tip on a Pixel launcher.

`expo prebuild` regenerates `android/…/res/mipmap-*/ic_launcher_foreground.webp`
and `drawable-*/splashscreen_logo.png` from these files, so **prebuild must run
after any change to them** — the build script does that. Skipping it leaves the
previous artwork in the APK.

`assets/images/app-image.png` and the `react-logo*.png` files are unused
leftovers from the Expo template and are not referenced by `app.json` or the
app.

### If the Gradle distribution download times out

Gradle 9.3.1 is **already cached** on this machine at
`C:\Users\Jahna\.gradle\wrapper\dists\gradle-9.3.1-bin`, so the wrapper does not
need to download it. If it ever has to, the wrapper uses a 10-second read
timeout which a slow connection can trip partway through the ~131 MB download.
Fetch it with a resumable client and drop it into the wrapper cache instead:

```bash
mkdir -p ~/gradle-dists && cd ~/gradle-dists
curl -L --retry 10 --retry-all-errors -C - \
  -o gradle-9.3.1-bin.zip \
  "https://services.gradle.org/distributions/gradle-9.3.1-bin.zip"

DIST=$(ls -d ~/.gradle/wrapper/dists/gradle-9.3.1-bin/*/ | head -1)
rm -f "$DIST"/*.part "$DIST"/*.lck
cp gradle-9.3.1-bin.zip "$DIST/"
```

Re-run `./gradlew`; it unpacks the cached zip without downloading.

## 4. Verify the APK

Use **`apksigner`**, not `keytool -printcert -jarfile`. `keytool` reads the first
certificate it finds inside the archive; it does not verify the APK's signature
at all, so it will happily print a signer for a corrupted or unsigned APK.
`apksigner verify` actually checks the signature schemes and tells you which
ones are present.

```powershell
$apk = "C:\Users\Jahna\Music\AQSMS-APP-main\frontend\android\app\build\outputs\apk\release\app-release.apk"

# Exit code 0 and "Verified using v2 scheme ... true" is what you want.
# The signer must be CN=Aqua Smart Monitoring System, NOT "CN=Android Debug".
& "C:\Android\Sdk\build-tools\36.1.0\apksigner.bat" verify --verbose --print-certs $apk

# File digest, for recording alongside the artifact
Get-FileHash $apk -Algorithm SHA256

# Install on a connected phone
& "C:\Android\Sdk\platform-tools\adb.exe" install -r $apk
```

`build-apk.ps1` already runs the `apksigner` step and prints the SHA-256, so this
section is for verifying an APK you did not just build with it.

## 5. Verification before building

```bash
cd frontend
npx tsc --noEmit                     # must be 0 errors
npx expo lint                        # must be 0 problems
npx --yes tsx tests/logic.test.ts        # logic, mappers, client vs mock Pi
npx --yes tsx tests/pi_server.test.ts    # real Flask + SQLite Pi server
npx --yes tsx tests/registration.test.ts # public caretaker registration + ingest
npx --yes tsx tests/roles.test.ts        # owner/caretaker permissions, disable/enable
```

The last three suites start the **real** Flask server against a **real** SQLite
database (a scratch file in the temp directory, never `aqsms.db`), so they need
the Pi server virtualenv:

```bash
cd pi-server
python -m venv venv
./venv/bin/pip install -r requirements.txt     # Windows: .\venv\Scripts\python.exe -m pip install -r requirements.txt
```

## 6. What is NOT covered here

- The app has **not** been run on a physical Android phone or emulator.
- It has **not** been tested against real Raspberry Pi hardware or sensor probes.
- The **HTTPS path has never been exercised**: no certificate has been generated
  and no handshake performed. If `certs/aqsms-ca.crt` is missing at build time,
  the APK will not trust the Pi's HTTPS — the plugin warns and skips rather than
  failing the build.
- Thresholds remain unapproved on the Pi (`approved = 0`, NULL limits), so every
  parameter reads **No Data** rather than a green **Safe**. That is deliberate
  and must stay that way until limits are confirmed in writing.
